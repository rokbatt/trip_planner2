# 모바일 전략 — Companion 모드

> 이 문서는 결정 기록입니다. 모바일 관련 작업을 시작하기 전에 `Claude.md`와 함께 읽으세요.

## 0. 한 줄 요약

모바일은 데스크톱 화면을 줄인 게 아니라 **역할이 다른 두 번째 제품 표면**이다.

```
PC/노트북  = PLANNER    여행 전, 4개 게이트로 결정한다  (지금 만든 것 그대로)
모바일     = COMPANION  여행 전날·여행 중, 확정된 것을 실행하고 기록한다  (새 셸)
```

브레인스토밍 보드를 폰에 반응형으로 접어 넣지 않는다. 4개 게이트를 한눈에 놓고 판단하는 행위는
화면 크기의 문제가 아니라 **작업 자체가 큰 화면을 요구**하기 때문이다.

## 2. 먼저 치워야 할 제약

1. **Google Maps가 동기 로드** — `index.html`이 `<script src>`로 Maps JS를 직접 부른다. 모바일
   첫 화면이 지도 로딩에 인질로 잡힌다. "오늘" 화면은 지도 없이 성립해야 하고, 지도는 **탭했을 때만**
   로드한다.
2. **`api/*.ts`가 정확히 12개 = Hobby 상한** (원칙 3-7에 이미 도달). 푸시·ics처럼 서버가 필요한
   모바일 기능은 새 파일을 만들 수 없다 → **Supabase Edge Functions로 뺀다.** 별도 쿼터이고,
   푸시 토큰은 어차피 Supabase 유저 테이블 옆이 제자리다.
3. **PWA 자산이 0** — manifest·서비스워커·앱 아이콘 전부 없음(`public/`엔 `hero.jpg` 하나),
   viewport에 `viewport-fit=cover`가 없어 노치·홈바 대응 안 됨.
4. `vercel.json`의 assets 외 `no-store` 정책은 **그대로 두면 된다** — 서비스워커 갱신엔 오히려 유리.

## 4. 모바일 정보구조

하단 탭 4개: **오늘 · 일정 · 지갑 · 준비**

"오늘" 탭은 고정 화면이 아니라 여행 단계에 따라 내용이 통째로 바뀐다.

- 여행 전 → D-day · 체크리스트 진행률 · 확정 일정 미리보기
- 여행 중 → **NOW 카드** (다음 한 곳 + 남은 시간 + 액션 3개)
- 여행 후 → 실제 기록 기반 리포트 · 정산 마무리

NOW 카드 규칙: 한 화면에 **다음 한 곳만**, 액션은 **도착 / 출발 / 밀기 세 개로 고정**,
지도는 기본으로 안 뜬다.

## 5. 실시간 타임라인 — 데이터 설계 (구현 완료, ✅)

실제 도착 시각을 `route_stops.arrive_time`에 쓰면 **안 된다.** 그 컬럼은 "사용자가 고정한 계획
시각"이고, 실제 시각으로 덮으면 계획을 되돌릴 수 없다. **별도 테이블로 분리한다:**

```
trip_stop_progress
  stop_key · trip_id · destination_id · day_index
  actual_arrive_at · actual_depart_at · status · recorded_by
```

- 계획(`route_stops`)은 불변, 실제(`trip_stop_progress`)만 쌓임 → 여행 후 리포트가 공짜로 생김
- Realtime publication에 추가 (links·expenses와 같은 패턴)
- **키를 `route_stop_id`가 아니라 `stop_key`(=`dayModel.ts`의 `TlStop.key`)로 잡았다** — 처음
  스케치와 다른 부분. `saveRouteDay`는 그 DAY를 저장할 때마다 route_stops 전체를 지우고
  다시 넣는 방식이라, FK로 걸었으면 관련 없는 정류지 하나만 수정해도 CASCADE로 그 날 진행
  기록이 통째로 날아간다. 실제 구현 단계에서 발견해 피한 함정 — `route_stops`를 참조하는
  테이블을 또 만들 때 반드시 되짚어볼 것 (`supabase/trip_stop_progress.sql` 상단 주석 참고)

**계산 로직은 새로 짤 게 거의 없다.** 기존 `computeStopTimes`는 09:00에서 시작해 "체류 + 이동"을
누적하는데, 실시간 모드는 **시작 시계를 마지막 실제 기록으로 바꾸는 것**이 전부다. 이미 있는
overrun/slack 개념(5-3)을 "이 속도면 마지막 일정 22:10 도착, 30분 초과"로 그대로 쓴다.
초과가 생겨도 자동으로 지우지 않고 제안만 한다 — 결정은 사람이.

## 6. 기능 우선순위

판단 기준은 하나: **"이 기능이 PC에서는 말이 안 되는가?"** 그런 기능만이 모바일 앱을 정당화하고,
동시에 App Store 심사를 통과시킨다.

**Tier 1 (앱의 존재 이유)**
1. NOW 카드 + 자동 밀림
2. 오프라인 팩 — 출국 전 일정·사진·주소 프리캐시. 지도는 Static Maps 스냅샷으로 대체(원칙 3-2)
3. 체크리스트 — 개인/공동 분리, 목적지·계절 템플릿, D-7 알림
4. 티켓 지갑 — 항공권·바우처 캡처를 비행기 모드에서 열람 (OCR은 넣지 않는다)
5. Quick Capture — 공유 시트로 담기. iOS는 네이티브 Share Extension 필요 → 앱 출시 명분
6. 현장 지출 기록 — 현재 정류지 기반 카테고리·통화 프리필

**Tier 2** — 동행 위치 공유(옵트인·기간 한정) · 잠금화면 위젯 · QR로 PC→폰 이어받기 ·
밤 9시 리캡 · ics 내보내기 · 여행 리포트

**하지 말 것**
- 예약·커머스 연동 (트리플·마이리얼트립과 정면 충돌, 몽실이의 무기와 무관)
- 실시간 대중교통·혼잡도 (근거 데이터 없음 — 원칙 3-1 위반). "구글맵에서 열기" 딥링크가 정답
- shortlist·route를 반응형으로 우겨넣기 (8,300줄을 접어봐야 아무도 안 씀)
- 알림 남발 — 하루 3개 상한, 실질 1~2개

## 7. 앱 출시 판단

**1단계 PWA (지금 가능)** — manifest + 아이콘(192/512/maskable) + 서비스워커 +
`viewport-fit=cover` + `env(safe-area-inset-*)`. 홈 화면 추가 시 전체화면.
안드로이드 웹푸시 가능, iOS는 16.4+ & 홈 화면 추가 시에만.

**2단계 스토어 (Capacitor)** — 바닐라 Vite라 **재작성 불필요**, `dist/`를 그대로 감싼다.
얻는 것: 네이티브 푸시(APNs/FCM), 위젯·라이브 액티비티, iOS 공유 시트 확장, 백그라운드 위치,
캘린더 쓰기. 비용: Apple $99/년, Google Play $25 1회.

> **가장 큰 리스크 — App Store Guideline 4.2 (Minimum Functionality).**
> "웹사이트를 그대로 감싼 앱"은 리젝된다. 회피책은 꼼수가 아니라 실제로 네이티브가 필요한 기능을
> 갖추는 것이고, 그게 정확히 Tier 1 목록이다. **그래서 순서가 결정적이다 — Tier 1을 만든 다음에
> 스토어에 간다.** Google Play는 기준이 훨씬 느슨해서 먼저 내도 된다.

⚠️ **확인 필요**: 동행 위치 공유를 넣는다면 국내 위치정보사업 신고 의무 대상인지 별도 확인이
필요하다. 이 확인 전까지 위치 기능은 착수하지 않는다.

TIMELINE(가로 스와이프 페이저) — 즉 M2다.

## 9. 모바일 셸이 지켜야 할 기존 원칙

- **숫자는 `travelEstimate.ts`에서만 만든다** — 실시간 밀림 계산도 이 파일에 함수를 *추가*하는
  방식이어야지 모바일 모듈 안에서 계산하면 안 된다 (5-3)
- **새 `api/*.ts` 파일을 만들지 않는다** — 기존 파일에 `kind` 분기로 합치거나 Supabase Edge
  Functions로 뺀다 (3-7)
- **모르는 값은 빈칸으로 남긴다** — 화면이 좁아 뭐라도 채우고 싶어지지만, 근거 없는 값은 만들지
  않는다. Before You Go의 옅은 `?` 처리와 같은 방식 (3-1)
- **API 호출은 화면 진입이 아니라 사용자 행동에서** — "활성 DAY만, 이미 받은 구간은 다시 묻지
  않음" 전략을 그대로 가져간다 (3-2)
- **취소·해제 수단을 먼저 설계한다** — "도착"은 잘못 누를 수 있다. 기록 취소 방법을 버튼보다
  먼저 정한다 (3-3)
