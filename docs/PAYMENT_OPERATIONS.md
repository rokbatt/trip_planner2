# 결제 운영 절차

결제를 연 뒤 운영자가 하는 일을 순서대로 적은 문서예요. 설계는 `docs/PAYMENT_DESIGN.md`, 진행 상황은 `docs/COMMERCIAL_READINESS.md`가 기준이에요.
구분: **확인** = 코드·공식 문서로 본 것 · **확인 필요** = 기관·계약·실제 운영으로 확인할 것. 법률 판단은 단정하지 않아요.

마지막 갱신: 2026-11-24

## 0. 지킬 것

| 하지 말 것 | 이유 |
|---|---|
| **PG사 관리자 화면에서 직접 결제 취소** | 포트원과 결제 상태가 어긋나요(포트원 안내, 확인). 취소는 항상 몽실이 관리자 칸 또는 포트원 콘솔로 해요 |
| `payments`·`user_plans`를 SQL로 직접 고치기 | 반영·회수는 DB 함수가 한 번만 하도록 만들어져 있어요. 직접 고치면 기간·웹 검색 수가 어긋나요. 예외: 관리자·지인 수동 PRO(`user_plans.sql`의 예시) |
| 결제 기록 지우기 | 대금 결제 기록 5년 보관(전자상거래법, 확인 필요). 정리 작업이 기간이 지나면 지워요 |
| 비밀값(API 시크릿·웹훅 시크릿)을 메일·채팅·코드에 쓰기 | Cloudflare Secret에만 넣어요 |
| 카드 번호 등을 메일로 받기 | 환불에는 결제 번호만 있으면 돼요. 몽실이는 결제 수단 정보를 저장하지 않아요 |

## 1. 정기 점검

### 주 1회 — 대사(포트원과 몽실이 기록 맞추기)
1. 포트원 콘솔 → 결제 내역에서 지난 7일 "결제 완료"·"취소" 건수와 합계를 봐요.
2. Supabase SQL Editor에서 아래를 실행해 같은 기간 숫자와 비교해요.
   ```sql
   select status, count(*), sum(amount) from payments where created_at > now() - interval '7 days' group by status
   ```
3. 반영이 안 된 결제(포트원은 완료인데 여기는 `ready`)가 있는지 봐요.
   ```sql
   select payment_id, buyer_email, created_at from payments where status = 'ready' and created_at < now() - interval '1 hour' order by created_at desc
   ```
   있으면 3장 "반영 다시 확인"으로 처리해요(포트원에서 완료인 것만 반영돼요).
4. 숫자가 다르면 Cloudflare 로그에서 `[pay]`를 찾아봐요(5장).

### 월 1회 — 정산
- 포트원(또는 PG) 정산 내역을 내려받아 보관해요. 이것이 매출 장부예요.
- 부가세·종합소득세 신고 시기와 방법은 과세 유형에 따라 달라요(**확인 필요**: 홈택스·세무서).

## 2. 환불 처리

### 순서
1. **접수**: `help@mongsil2.com`으로 온 "[몽실이] 환불 요청" 메일에서 결제 번호(`mongsil-…`)를 확인해요.
   - 요금제 화면의 "환불 요청" 버튼은 결제 번호를 메일에 미리 넣어 줘요.
   - 결제 번호가 없으면 보낸 이메일로 찾아요.
     ```sql
     select payment_id, amount, status, created_at from payments where buyer_email = '보낸사람@example.com' order by created_at desc
     ```
2. **검토**: 몽실이에 관리자 계정으로 로그인 → 계정 메뉴 "요금제 · PRO" → 맨 아래 **"관리자 · 결제 처리"** → 결제 번호 입력 → **환불 검토**
   - 결제자, 금액, 결제일(며칠 지났는지), 결제 후 PRO 기능 사용 횟수, 기준 안/밖이 나와요.
3. **판단**(아래 기준표)
4. **실행**: 환불 사유를 적고 **이 결제 환불하기** → 확인 창 → 포트원 취소 → 이용권 회수
   - "포트원 취소에 실패했어요"가 나오면 포트원 콘솔에서 그 결제 상태를 확인해요. 이미 취소돼 있으면 웹훅이 이용권을 회수해요.
5. **답장**: 7장 문구로 회신해요. 카드 환불이 실제로 들어오기까지는 카드사·간편결제사에 따라 며칠 걸릴 수 있다고 안내해요.

### 판단 기준

| 상황 | 처리 | 근거 |
|---|---|---|
| 결제 후 7일 이내 + PRO 기능 사용 0번 | **전액 환불** | 결제 전 고지(확정 2026-11-24) |
| 같은 날 두 번 결제(실수) | 하나 **전액 환불**(두 결제 모두 반영돼 기간이 60일이 된 상태라, 하나를 환불하면 30일로 돌아가요) | 중복 결제 |
| 서비스 장애로 PRO 기능을 못 씀 | **환불**(사용 기록이 있어도) | 회사 책임 |
| 미성년자가 법정대리인 동의 없이 결제 | **취소**. 법정대리인임을 어떻게 확인할지는 **확인 필요**(전문가·소비자원 안내) | 결제 전 고지, 민법 |
| 7일 이내지만 PRO 기능을 씀 | 원칙적으로 청약철회 제한. 정중히 안내(7장). 애매하면 환불 쪽으로 | 결제 전 고지, 전자상거래법 제17조(확인 필요) |
| 7일이 지남 | 원칙적으로 환불 없음. 장애·중복 결제면 위 기준 | 결제 전 고지 |
| 탈퇴한 사람의 문의 | 결제 기록은 남아 있어요(`buyer_email`로 조회). 이용권은 이미 사라졌으니 환불 기준만 판단 | 설계 5장 |

- "PRO 기능 사용" 기록은 **7일만 보관**돼요(`api_usage`).
  - 7일 환불 기간에는 충분하지만, 그 뒤 분쟁 자료로는 남아 있지 않아요(6장).

## 3. "결제했는데 PRO가 안 돼요"

1. 결제 번호를 받아요. 없으면 이메일로 찾아요(2장 SQL).
2. 관리자 칸에 결제 번호를 넣고 **반영 다시 확인**을 눌러요.

| 결과 | 뜻 | 할 일 |
|---|---|---|
| 결제 완료 — 이용권이 반영돼 있어요 | 정상이에요(웹훅이 늦었거나 화면이 옛 정보) | 앱을 새로고침하라고 안내 |
| 아직 결제 승인 전 | 결제창에서 끝나지 않았어요 | 포트원 콘솔에서 상태 확인. 실제 출금이 없으면 결제가 안 된 것 |
| 결제가 완료되지 않은 주문 | 실패·취소된 결제예요 | 출금이 있었다면 PG 취소 대기일 수 있어요. 포트원 콘솔 확인 |
| 금액·상점·채널이 맞지 않아 반영하지 않음 | **반영하면 안 되는 결제**예요(위·변조, 테스트 결제가 운영에 들어옴 등) | 포트원 콘솔 확인 → 실제 돈이 빠져나갔으면 **포트원 콘솔에서 취소** |
| 확인에 실패 | 포트원·DB 일시 오류 | 잠시 뒤 다시 |

## 4. 수동 PRO(관리자·지인·보상)

- 돈을 받지 않고 PRO를 주는 경우예요. `supabase/user_plans.sql` 아래의 예시 SQL을 써요.
- 결제로 생긴 이용권(`source='portone'`)이 있는 사람에게 수동 PRO를 덮어쓰지 마세요. 기간이 어긋나요. 보상으로 기간을 늘려야 하면 그 SQL을 Claude에게 만들어 달라고 해요.

## 5. 장애·로그

로그는 Cloudflare → Workers → mongsil → **Observability**에서 `[pay]`로 찾아요.

| 로그 | 뜻 | 할 일 |
|---|---|---|
| `[pay] 서버 설정 없음: …` | Secret·변수 이름이 빠졌거나 틀렸어요(빠진 **이름**만 나와요) | Cloudflare 변수 확인 |
| `[pay] 웹훅 서명 실패` | 시크릿이 틀렸거나, 우리 것이 아닌 요청이에요 | 연속으로 나오면 웹훅 시크릿 확인(6장 교체 순서) |
| `[pay] mismatch amount/store/currency/test_channel …` | 반영을 거절한 결제예요 | 3장 "금액·상점·채널" 행 |
| `[pay] 포트원 조회 실패 4xx/5xx` | API 시크릿 오류 또는 포트원 장애 | 401·403이면 API 시크릿, 5xx면 포트원 공지 확인 |
| `[pay] 부분 취소 수신 — 수동 확인 필요` | 이 상품에는 없는 부분 취소가 들어왔어요 | 포트원 콘솔 확인 후 Claude와 처리 |
| `[pay] grant_pro_pass 실패 …` | DB 함수 오류 | 웹훅이 다시 보내 줘요. 계속되면 Claude와 확인 |

결제가 반복해서 실패하면 결제를 잠시 닫을 수 있어요. Build 변수 `VITE_PORTONE_STORE_ID`를 비우고 다시 배포하면 요금제 화면이 "결제 준비 중"으로 돌아가요. 이미 결제된 건의 반영과 웹훅은 서버 Secret이 있는 한 계속 동작해요.

## 6. 시크릿 교체 · 분쟁

### 웹훅 시크릿·API 시크릿 교체
1. 포트원 콘솔에서 새로 발급해요.
2. Cloudflare Worker Secret(`PORTONE_WEBHOOK_SECRET` 또는 `PORTONE_API_SECRET`)을 새 값으로 바꿔요.
3. 포트원 콘솔의 웹훅 "호출 테스트"를 눌러요. 로그에 서명 실패가 없는지 봐요.
4. 옛 시크릿을 폐기해요.

웹훅 시크릿은 2와 3 사이에 잠깐 서명이 맞지 않을 수 있어요. 그 사이의 웹훅은 포트원이 다시 보내요(재시도 정책은 **확인 필요**).

### 분쟁(차지백)
- 포트원 웹훅 `Transaction.DisputeCreated`는 지금 서버가 **무시**해요(기록만 하지 않음). 포트원 콘솔·메일 알림으로 알게 돼요.
- 소명 자료로 쓸 수 있는 것은 결제 기록, 결제 전 고지와 동의(화면에서 체크해야 결제 가능), PRO 사용 기록이에요.
  - PRO 사용 기록은 7일 보관이라 늦게 온 분쟁에는 없을 수 있어요.

## 7. 답장 문구 (진지한 문체 — 합니다/주세요체)

**환불 완료**
> 안녕하세요, 몽실이입니다. 요청하신 결제(결제 번호 {결제번호}, {금액}원)를 환불했습니다.
> 카드사·간편결제사 사정에 따라 실제 환불까지 영업일 기준 며칠이 걸릴 수 있습니다. 이용해 주셔서 감사합니다.

**환불이 어려운 경우(7일 이내지만 PRO 기능 사용)**
> 안녕하세요, 몽실이입니다. 문의하신 결제(결제 번호 {결제번호})는 결제 후 PRO 전용 기능을 사용하신 기록이 있어,
> 결제 시 안내드린 기준에 따라 청약철회가 제한됩니다. 이용에 불편이 있으셨다면 구체적인 내용을 알려 주세요. 다시 확인하겠습니다.

**반영 확인 완료**
> 안녕하세요, 몽실이입니다. 결제(결제 번호 {결제번호})가 정상적으로 반영된 것을 확인했습니다.
> 앱을 새로고침하시면 PRO 기능을 이용하실 수 있습니다. 불편을 드려 죄송합니다.

## 8. 출시 전 최종 점검
`docs/COMMERCIAL_READINESS.md` 3단계 E의 목록대로 해요. 테스트 결제로 반영·중복 웹훅·금액 조작·만료·웹 검색 100번을 확인하고, 실결제 소액 1건으로 결제 → 반영 → 환불 → 회수를 확인해요.
